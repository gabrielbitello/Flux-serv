# Production Deploys

How a `git push` becomes a running prod release — without a build on your
PC and without downtime.

## Flow

```
GitHub Actions (push to main)
  → POST https://flux.bitello.xyz/api/projects/{name}/deploy
      body: { ref, actor, run }   Bearer: project deploy token
  ← 202 Accepted (deploy is asynchronous — the request never waits for a build)
  → fluxd background pipeline:
      git fetch origin → ancestry guard → immutable release dir →
      blue-green switch with drain → deploy_log + events trail
```

The workflow template lives at
[`doc-old/templates/deploy-workflow.yml`](../doc-old/templates/deploy-workflow.yml)
(install with `flux init ci` once that command lands; today, copy it by
hand). One-time GitHub setup:

```
gh secret set FLUX_DEPLOY_TOKEN      # output of `flux project token <name>`
gh variable set FLUX_PROJECT --body <project name>
```

## The public route, closed by default

The deploy route only exists if the global config says so:

```toml
[deploy]
public_route = true   # default false — the path 404s without this
```

Everything is born closed: no new public surface exists without an explicit
decision in config (`crates/flux-common/src/config.rs`, `deploy_public`,
tested to answer 404-brandished when absent).

## Gate order (each stage before the next)

From `crates/fluxd/src/deploy.rs`:

1. **Method** — anything but `POST` ⇒ 404 (GET never burns limiter tokens).
2. **Per-project rate limit, before auth** — dedicated bucket, **10/min with
   burst 10**: the 11th request in a burst gets `429` + `Retry-After`. Abuse
   in one project cannot dry out another's budget.
3. **Registration** — unknown project ⇒ 404.
4. **Auth, fail-closed** — sha256 of the Bearer compared (constant-time)
   against `deploy_tokens` in SQLite; **401** (bad token), **403** (no token
   for the project) and **503** (state unavailable) are distinct answers.
   Tokens are generated by `flux project token <name>` — CSPRNG, shown
   once, regeneration revokes the previous hash.
5. **Concurrency** — one deploy per project: the second while one is in
   flight gets **409** (in-memory guard).
6. **202 Accepted** — from here the pipeline runs in the background.

## Background pipeline

- `git fetch origin` + **ancestry guard**: the pushed SHA must be a
  descendant of the deployed one — an orphan/forced SHA is refused
  (protects against rewriting history into prod).
- **Immutable release directory** `/srv/flux/releases/{name}/{sha}` checked
  out via `git worktree` — releases are never mutated in place; every git
  command runs with a **120 s timeout** (`kill_on_drop`), so a git hung on
  the network cannot hold the concurrency guard forever.
- **Health gate before the switch** (`[health] path`, 06): RUNNING is not
  enough — the switch waits until the new color's `app` container actually
  **answers GET `{health.path}`** (30 × 1 s probes, 2 s timeout each, direct
  to the container IP over the Docker network). A wrong path or a broken app
  aborts the switch BEFORE the pointer moves — the old color keeps serving.
- **Blue-green switch**: the router flips the host to the new color; the old
  color is drained with `docker stop -t` (graceful). Rollback is the same
  mechanism in reverse — switch back to the previous release. The whole path
  was proven live (blue→green switch on the same domain, drain, switch-back).
- Every step writes to `deploy_log` and the event trail — a deploy with no
  trail is a bug, not a success.

## Known gaps (honest list)

From the implementation status (see [status.md](status.md)): the CI step
that **builds the image and starts the inactive color** (scenario B) is the
next cut; `flux prod rollback` and release rotation (keeping N old releases)
are pending phases. The switch/drain/rollback mechanics themselves are done
and verified.
