Redigido em 2026-10-14 a partir das rodadas E1/E2/E3 do workflow e das três auditorias independentes — todas incorporadas ao texto abaixo; as anotações "correção da auditoria" marcam o ponto exato de cada correção.

## Objetivo

Usar tuxones/actions-runner-k8s como material de estudo para criar um repo PRÓPRIO de self-hosted GitHub Actions runners: pegar as melhores partes (ARC scale set, efêmero 1 pipeline=1 runner, DinD, runbook), consertar os pontos fracos deles (estado fora do git, pinning solto, build manual sem CI, imagem monolítica pesada) e integrar diretamente com o Flux-server. Prioridade máxima do Gabriel: leve e rápido — o runner da Tuxon é lento e pesado.

## Critérios de sucesso

1. Repo próprio versiona TODO estado de deploy em git (values/manifests do runner), zero `kubectl patch` manual como fluxo oficial.
2. Runner efêmero: 1 job = 1 container/pod, teardown automático provado com job de teste.
3. Imagem enxuta mensurável: tamanho da imagem e cold start (pull+ready) medidos e comparados ao runner da Tuxon; meta declarada no plano.
4. Pipeline E2E: push num projeto de teste → runner executa workflow → fluxd recebe intenção de deploy (spec 10: `curl` + `FLUX_DEPLOY_TOKEN`) → release criado na VM.
5. CI no próprio repo builda e testa a imagem runner quando Dockerfile muda.
6. README/runbook cobre: instalação, debug (TooManyPodFailures, runner deprecated), disco, atualização de versão.
7. Aprendizado documentado: o que copiar do tuxon, o que consertar, por quê — nada copiado verbatim.

## Restrições

- Estudo apenas: nada copiado verbatim do repo privado da Tuxon; conceitos, comandos e arquitetura ok.
- Não tocar na infra da Tuxon nem usar credenciais deles no repo novo.
- Stack Flux: Rust, docker compose na VM VirtualBox; host Windows 11 Home sem Hyper-V.
- k8s não existe hoje no ambiente do Gabriel (FATO) — ARC exige Kubernetes; escolha do runtime (k3s na VM vs runner docker efêmero sem ARC vs outro) é decisão central do plano, com trade-off peso/leveza explícito.
- Integração segue spec 10 do Flux: action manda INTENÇÃO (curl HTTPS + `FLUX_DEPLOY_TOKEN` via túnel), nunca SSH; fluxd faz fetch/build/blue-green.
- Commits locais; push só por pedido do Gabriel.

## Fora de escopo

- Migrar/alterar infra da Tuxon.
- Deploy real de clientes/projetos de terceiros.
- Implementar o plano (esta rodada produz só o plano orquestrado).
- Painel web (spec 08) e observabilidade (spec 13) além do que a integração exigir.
- Fork A/B do gate de deploy e outros pendentes do STATUS que não tocam runners.

## Filosofia

Docker que JÁ existe na VM + systemd, zero runtime novo: k8s/ARC é o peso que a prioridade "leve e rápido" manda cortar numa VirtualBox que já serve prod. A imagem do runner é o ativo — fica ~constante (toolchain de projeto por job-container, no modo opt-in do socket) e migra inteira se um dia ARC entrar. As dependências ocultas das duas auditorias viraram decisão EXPLÍCITA, não improviso: rota de deploy é a ÚNICA exceção pública da API :7420 (`crates/fluxd/src/lib.rs:66`), nestada sozinha com Bearer + layer de rate limit PRÓPRIO (a borda global não parametriza por rota — `edge.rs:14-18`) + flag; token é POR PROJETO de verdade com migration de schema versionada; docker CLI + socket é opt-in ÚNICO (juntos ou nada); `token.sh` fala REST com curl porque gh não existe na VM; spawner é ÚNICO (systemd executa `docker compose run --rm`) com backoff contra crash-loop; pool endereçável por `GITHUB_REPO` porque runner repo-scoped não recebe job de outro repo; snapshot VirtualBox antes de mutar a VM que serve prod. Seguro onde o sinistro é caro: pin por digest + SHA256, `mem_limit`, compose project distinto do Flux, token revogável por projeto, endpoint atrás de flag, CI em ubuntu-latest para nunca depender do runner que conserta. Teste caro onde a falha custa de verdade: teardown provado 5x seguidas com re-registro sob rate limit, gate de CI provado vermelho, E2E com token real pela cadeia pública. Toda vitória contra a Tuxon vira número medido em `MEDICOES.md`, não adjetivo.

## Riscos e mitigações

1. **Pool apontando para o repo errado:** runner repo-scoped não recebe job de outro repo — E2E fica em queued eterno (atenção da auditoria final). *Mitigação:* `GITHUB_REPO` como variável do `.env`; comutação de repo = commit + `make install` (passo NOMEADO da F5, com commit de volta ao repo runner); debug do runbook cobre 'queued = pool apontando pro repo errado'. Risco residual assumido: comutação esquecida trava o run seguinte — visível como queued, não silencioso.
2. **gh indisponível/instável dentro da VM:** binário só no host Windows, auth em keyring por usuário — frágil sob systemd root (atenção da auditoria final). *Mitigação:* token.sh fala REST direto com curl (PAT do `.env`) — correção incorporada na F2; gh continua só no host para checagens (gh api de runners órfãos, `gh secret set`).
3. **VM que serve prod mutada sem ponto de restauração:** 'VM limpa' não existe no ambiente; instalar por cima é one-way (atenção da auditoria final). *Mitigação:* snapshot VirtualBox ANTES da F2, citado no runbook; instalação do zero roda sobre o snapshot, nunca sobre o estado vivo. Risco assumido residual: snapshot consome disco do host — deletável após a F6 com o rollback de bump provado.
4. **Meta de tamanho impossível no fallback:** com proxy docker:dind (~300-430 MB), 50% ≈ 150-215 MB — abaixo do tarball do runner (~500 MB incompressíveis) que o próprio plano declara (atenção da auditoria final). *Mitigação:* meta CONDICIONAL declarada na F0: relativa (≤50%) só com baseline real; sob proxy, meta absoluta rotulada (≤1 GB, tarball ~500 MB como piso); estouro vira delta medido e decisão do Gabriel com número.
5. **Crash-loop martelando a API de registration-token:** PAT inválida ou rede fora com `Restart=always` puro = requests contínuos do GitHub a partir da VM de prod, piorando o estado (atenção da auditoria final). *Mitigação:* `RestartSec=15` + `StartLimitIntervalSec=300/StartLimitBurst=5` na unit; seção do crash-loop no runbook cobre esse loop exato; POOL_SIZE=1 limita o martelo a uma instância.
6. **Supervisor duplo ambíguo:** 'docker run --rm' no texto e compose.yaml coexistindo — drift vira container parado sobrando e dúvida de comando em incidente (atenção da auditoria final). *Mitigação:* spawner ÚNICO: systemd executa `docker compose run --rm runner`; compose.yaml é a única fonte de env/rede/labels, sem restart policy; incidente = `systemctl stop flux-runner`, um comando só.
7. **Repo de teste privado sem credencial de leitura na VM:** fluxd não faz git fetch do SHA e o deploy falha; `flux repo add` (spec 10:25) não existe no CLI (grep vazio em `crates/flux-cli/src/main.rs` — verificado nesta rodada) (atenção da auditoria final). *Mitigação:* flux-runner-e2e nasce PÚBLICO (deploy de teste não precisa privacidade); se um dia virar privado, pré-requisito EXPLÍCITO de credencial de leitura na VM antes do push — nunca descoberto em runtime.
8. **Rate limit 10/min 'de graça' da borda R30 não existe:** EdgeLayer é global único (`router.rs:35`) e per-projeto/rota é FUTURO (`edge.rs:14-18`) (atenção da auditoria final). *Mitigação:* layer tower aninhado SÓ na rota de deploy com EdgeLimits próprio (10/min, burst pequeno) — `Bucket::take` (`edge.rs:137`) aceita rate/burst por chamada; borda global R30 intocada; rate limit genérico por projeto continua no roadmap.
9. **Job fantasma trava o slot único:** container morto no meio do job deixa o run 'running' até o timeout default do GitHub (até 6 h) na POOL_SIZE=1 (nota da auditoria final). *Mitigação:* job de teste com `timeout-minutes: 10` — falha cedo, libera o slot; runbook cobre 'job preso em queued = pool morta'.
10. **Token por projeto sem migration de schema:** SQLite do fluxd versiona schema com recusa de adulteração — hash novo sem versão nova quebra a abertura do banco (nota da auditoria final). *Mitigação:* correção incorporada na F4: migration de schema nomeada via `settings.schema_version` (`state.rs:13-14`, guard com recusa de adulteração em `:432-450`); critério de pronto exige fluxd sob schema antigo reagindo com erro claro.
11. **Disco cresce sem teto:** imagens do baseline (GBs) esquecidas no cache docker da VM de prod e `/srv/flux/releases` sem rotação até a R10 completa (nota da auditoria final). *Mitigação:* correções incorporadas: `docker rmi` do baseline e candidatos perdedores na F0; rotação de releases (spec 10:48, rotação 5) listada como lacuna no STATUS R10 PARCIAL — teto volta na R10 completa.
12. **Bump ruim sem caminho de volta:** 'runner deprecated' persistente após bump quebrado (nota da auditoria final — o ciclo da Tuxon só sabia subir). *Mitigação:* correção incorporada na F6: rollback documentado como entrada própria — `git revert` do commit do bump + `make install` + run verde de confirmação; snapshot da F2 como último recurso.
13. **I/O de VirtualBox estoura a meta de cold start (≤ 60 s)** — disk I/O virtualizado é o gargalo típico (risco desde a rodada 1, meta já condicional). *Mitigação:* imagem 100% local (zero pull externo em produção); meta condicional declarada com número; estouro vira delta documentado em MEDICOES.md e decisão de otimizar fica com o Gabriel.
14. **F4 (fluxd) incha:** R10 é NÃO inteiro hoje e a spec 10 completa é grande (blue-green, drain, static serving). *Mitigação:* recorte mínimo documentado (intent + release, sem blue-green); gate da fase é o curl 202 + release; se inchar, cenário B: endpoint grava intenção + cria release-dir sem subir container, pipeline real vira fase própria da R10 — declarado, não improvisado.
15. **Conflito de push:** critérios 4 e 5 do objetivo exigem push ao GitHub, e a regra é push só por pedido do Gabriel. *Mitigação:* cada fase termina commitada; os 2 pontos de push (repo runner na F3, repo de teste na F5) pedem ok explícito no momento, seguindo o protocolo de interação.
16. **PAT de longa vida no `.env` da VM:** credencial de registro em disco (risco da rodada 1, mantido). *Mitigação:* PAT fine-grained com escopo mínimo (fallback classic repo-scoped curto), `.env` gitignored com placeholder; runner no nível de repo, nunca org; vazamento = revoke + regenerar + `make down`.
17. **Socket docker montado no runner (modo opt-in) = escape de container** para quem controla o job — mesma classe do dind privileged da Tuxon (bloqueante 3 resolvido como opt-in; o risco do opt-in em si é assumido, não eliminado). *Mitigação:* RISCO ASSUMIDO com cerca: opt-in ÚNICO documentado = compose override com CLI + socket JUNTOS, nunca no default (grep prova); risco escrito no runbook com a resposta a incidente (revoke PAT + `make down`); default roda só job curl, sem `container:`.
18. **Runner executa código do próprio Gabriel em single-user:** a superfície de escape (socket opt-in, rota pública de deploy) existe num ambiente single-user — ameaça real só se terceiros passarem a mandar job (risco da rodada 1, mantido). *Mitigação:* consciência explícita: runner registrado POR REPO, labels restritos, risco registrado no bloco 'o que NUNCA fazer' do estudo; revisitar se o runner um dia executar código de terceiros.
